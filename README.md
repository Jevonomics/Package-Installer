# Package Installer

A two-minute survey turns a student's actual tasks (resumes, interviews, cold outreach, coursework, and so on) into a personal bundle of 1-3 real AI tools per task, each with a setup guide and a ready-to-paste prompt.

This repo is the static-site build. It pairs with a Claude Artifact build of the same product that has a shared pilot database and a researcher dashboard; this build trades that away for a plain GitHub + Vercel deploy that can actually call DeepSeek server-side.

## What's here

- `index.html`, `catalog.js`, `app.js`: the whole app. No build step, no framework.
- `api/recommend.js`: one serverless function. Takes a tester's survey answers and the tools already matched to them, and asks DeepSeek to rewrite each tool's "why this fits" line for that specific person. Everything else (which tools exist, their links, setup guides, prompts) stays in `catalog.js` and is never generated by the model.

## Running it locally

```
npm install -g vercel   # one-time, if you don't have it
vercel dev
```

Vercel's dev server serves `index.html` as-is and runs `api/recommend.js` as a real serverless function on the same origin, so `fetch('/api/recommend')` in `app.js` works without any extra config.

If you skip Vercel and just open `index.html` directly in a browser (or serve it with any plain static server), the app still fully works: the survey, bundle, and dashboard don't need a backend. The only thing that's missing is the AI-personalized blurbs, since there's no server to run `api/recommend.js`. The app is built to fail open: no backend reachable just means every tool keeps showing its default static rationale.

## Using the DeepSeek key

1. Copy `.env.example` to `.env` and paste your real key into `DEEPSEEK_API_KEY=` for local testing. `.env` is already gitignored; it must never be committed.
2. For the deployed site, set `DEEPSEEK_API_KEY` as an environment variable in your host's dashboard (Vercel: Project Settings, Environment Variables), not in any file in this repo.
3. If the key is ever pasted into a chat, a doc, or any other place outside your own `.env`/host dashboard, rotate it. Treat it as compromised the moment it leaves those two places.

Without the key set, `/api/recommend` still responds successfully; it just returns no personalization, and the UI falls back to its static copy. Nothing breaks.

## Deploying

Vercel is the easy path: it auto-detects the static files plus the `api/` folder with zero config.

```
vercel login
vercel --prod
```

Then add `DEEPSEEK_API_KEY` under Project Settings, Environment Variables, and redeploy.

GitHub Pages won't work for the full experience: it only serves static files, so `api/recommend.js` would never run and the AI personalization would stay off permanently (which is still a perfectly fine way to run the pilot, just without that one enhancement).

## What's intentionally missing from this build

- **No shared database.** Survey answers and toolkit state save to `localStorage`, so they're per-browser. Two different devices for the same student look like two different people. There's no cross-tester aggregate view here; that lives in the Claude Artifact build.
- **No real authentication.** Name and email are typed in, not verified. Fine for a trusted pilot group, not for a public launch.
- **DeepSeek only rewrites copy, it doesn't choose tools.** The survey-to-tools matching is a static lookup in `catalog.js`. This was a deliberate safety choice: letting a model freely recommend tools would risk inventing sign-up links or features that don't exist. If you want the matching itself to be AI-driven later, that's a bigger change and worth doing carefully.
